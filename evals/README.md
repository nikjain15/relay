# Evals

The 300-household book under [`public/samples/`](../public/samples/) is the evaluation corpus. Every
agent runs over it in `npm run check`, and the run fails on any finding missed, any finding raised
that should not have been, any number the engines get differently from the eval's own arithmetic, and
any record that is incoherent as data.

## What is in the corpus

| File | Rows | What |
|---|---:|---|
| `public/samples/clients.csv` | 300 | Households across the three advisors: two people or one, ages, monthly spending, cash, core portfolio, an optional single-name holding with its 90, 60 and 30 day history, the household's own liquidity and concentration rules, Longevity and Legacy targets, last contact, a note from the last conversation, trusted contact on file, any unusual disbursement or new third party |
| `public/samples/messages.csv` | 585 | Captured messages, both directions, on email and text, from a fixed set of sentences |
| `public/samples/research-note.md` | 1 | A document to drop on the retrieval agent |

The corpus is generated by `scripts/build-samples.ts` from `lib/import/sample.ts` with a fixed seed, so
it is reproducible and every message and note is one of a known set of sentences. That is what makes
the ground truth checkable by hand: [`labels.json`](labels.json) says, for each sentence, which rule
should fire on it and which discovery kind it should yield, with the reason written next to the one
that fires nothing.

## How the expected side is built

[`expected.ts`](expected.ts) reads the CSV files with its own reader and imports nothing from `lib/`.
For every household it derives:

- Liquidity months as the whole number of months of spending held in cash, and total assets as the sum of the three holdings
- the opportunities the import should detect: liquidity below the household's target, a single name over the household's limit, no contact in more than 180 days
- which account rules should fire, from the rule parameters in `data/compliance/rules.json`: the specified-adult rule from the ages and the protection flags, the concentration rule from the holding against the firm's maximum, the drift rule from the 90 day history against the drift and headroom parameters
- which message rules should fire, from the labels, the direction, and whether the rule is in force after the firm-layer edits in `data/compliance/edits.json`
- which findings should come back as cannot evaluate rather than fire or clear, from the advisor's connections in `data/advisors/`, and which messages sit on a source that is not healthy and so are never swept
- which discovery kinds should be raised, from the labels on the messages and the note

It also checks the corpus as data ([`coherence()`](expected.ts)): ages in range, spending under a
tenth of assets a year, cash a whole number of months, the liquidity target at or above the minimum,
history only for holdings that exist and rising to today, every message on a known household and channel.

## How the engines are scored

[`run.ts`](run.ts) loads the two CSV files through the real import path (`parseCsv`, `mapClients`,
`mapMessages`, `clientErrors`), runs the sweep for each advisor, the discovery agent, a briefing per
household and retrieval per opportunity, and scores each against the expected side at the level of
(household, rule) and (household, kind). Precision and recall are reported per rule and per kind, and
every disagreement is named in the report rather than averaged into a percentage.

[`golden.json`](golden.json) holds the counts the run must reproduce. A change to a rule, an
extractor, the mapper or the corpus changes the golden, and the test fails until someone regenerates
it and looks at the diff.

```bash
npm run eval          # print the report and compare with golden.json
npm run eval:write    # regenerate REPORT.md and golden.json after an intended change
npm run test -- tests/evals
```

The current report is [`REPORT.md`](REPORT.md).

## What the eval has caught

Recorded here so the eval is not mistaken for a formality.

| Found | Where | Fix |
|---|---|---|
| A client asking to talk through their pension was not a retirement candidate; 53 of 85 expected retirement candidates were missed | `lib/discovery/discover.ts` | The extractor now reads a request to talk through a pension as the decision it is |
| 53 households had a liquidity target below their own minimum, and one spent a third of its assets a year | `lib/import/sample.ts` | Spending is anchored to the portfolio at 1.5% to 5% a year; the target is never below the minimum |
| One household's day-90 concentration was negative | `lib/import/sample.ts` | History is floored above zero |

The eval was also seen failing on each of four deliberate breaks before it was recorded as a guard: a
complaint pattern with two of its phrases removed, the retirement extractor narrowed, one household's
cash changed in the CSV, and the review threshold moved from 180 to 200 days.

## Limits

The corpus is synthetic and its sentences come from a fixed set, so recall of 100% here says the
engines read every sentence in that set, not that they read every way a client might say the same
thing. Sentences a real book would contain and these engines would miss belong in `labels.json` with
the finding expected, so the eval fails first and the engine is fixed second.
