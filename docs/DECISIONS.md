# Relay decisions

Append-only. Relay-local decisions use the **R-** sequence. Job-search decisions **D-49 to D-76** live in
`nikjain15/nik-jain-jobos` `DECISIONS.md`, stay binding, and are not restated here.

**R-01 to R-08 were lost.** They were written in a session that could not create this repository and
committed them only inside an ephemeral container. Their content survives only where the job-search
repo describes it (commit `281aed5`, D-71 to D-73, and the third audit). **Numbering resumes at R-09**
so that nothing collides if a copy of the original R-01 to R-08 ever resurfaces.

| # | Decision | Notes |
|---|---|---|
| **R-09** | **This repository was rebuilt on 2026-09-26 from the last reachable Relay documents, PRD v0.3, not from the lost v1.0** | The v1.0 PRD, `ARCHITECTURE.md`, `BUILD-SPEC.md` and the five diagrams were never pushed and are not reconstructed here: rewriting them from memory would produce a confident second version nobody can check. To the engine's builder it read as a verdict on the engine, against D-58. Reversible: v0.3 is in git history if Nik prefers it |

| **R-12** | **The recipient counter counts persons, firm-wide, per communication, excluding institutional investors, over the 30 calendar days ending on each send** | Third audit, Finding 2. FINRA 2210(a) counts retail investors; a household of two is two, and a template used by several advisors is one communication. Implemented in `lib/recipients/count.ts` with boundary tests at 24, 25 and 26, a 13-household case and a two-advisor case |
| **R-13** | **The human-gated-outward invariant is enforced, and has been seen failing** | `npm run check` runs typecheck, lint, `invariant:imports` and tests. Proven 2026-09-26: `node:https`, bare `https` and `undici` in `app/` or `lib/` fail dependency-cruiser; a global `fetch` POST and a send verb in `ACTION_VERBS` fail vitest; a model client in `lib/ranking/` fails dependency-cruiser; the clean tree passes. Patterns carry the fix found in `roleos-app` (dependency-cruiser resolves `node:https` to `https`) |
| **R-14** | **BUILD-SPEC v2.0 written fresh from PRD v0.4, then the prototype built to it: six surfaces, measurement, three designed-not-built pages, no model calls** | Per job-search D-73, spec before code. Deterministic engines for constraints, ranking, recipients and policy, each tested; the PRD's worked example holds (long-term lots into the core model eligible, all lots rejected for holding period; property proceeds fund Liquidity only through Treasury, money market or municipal ladder). Proven by `npm run check` (35 tests) and a 22-assertion browser run of the demo path with zero console errors. Two decisions made while building are written back into the spec: funding source as part of the output space, and refusal propagating to proposals |
| **R-15** | **Personas are cited composites: invented names and exact figures inside published ranges, each detail traced to a public source. Real UBS advisor teams are cited as evidence, never used as the persona** | Nik asked for personas grounded in real UBS advisors and clients so the work reads as researched. Real client data is not obtainable, and invented detail attached to a real advisor or client would misrepresent a real person in front of the firm, against job-search rule 1 and D-56. Instead `docs/PERSONAS.md` gives every persona detail a kind (Published, Derived, Chosen) and a source: UBS New York team pages for the founder, cross-border, family and entrepreneur practices; UBS's tiers, WAC disclosure and Wealth Way pages; SEC and IRS rules. Research changed one figure: Advisor B's load is **about 1,000 households**, not about 900, from UBS's 200+ professionals serving 200,000 to 300,000 clients. Shown in the PRD (Appendix A), the prototype (`/personas` and a "built from" box on each household) and the walkthrough mockup. Sources were read through search summaries; the ones marked **check** need one look by eye |
| **R-16** | **All client and reference data lives in `data/`, one JSON file per client, and every consumer reads it through `lib/data`** | Nik asked for client data in a separate document that can be changed easily and fetched at any time, so retrieval and chat are grounded in it. `data/clients/<id>.json` holds each complete record, including contact history, team notes and tasks; shared files hold advisors, products, documents, the batch cohort and prior sends. `getClientFile(id)` returns the grounding bundle: the client, their advisor, their opportunities and every document those cite. The old fixture modules are now thin views over `data/`. The walkthrough mockup no longer carries its own copy: `scripts/build-walkthrough.ts` generates `data/generated/walkthrough.json` with the real engines, and `npm run data:check` inside `npm run check` fails if it is stale (seen failing on a deliberate edit). Validation is seen failing on a broken holdings total. Plain-English titles, client openers and product phrases were added to the data so the drafts read plainly. A cash-cushion opportunity was added for Pell so the fourth story is backed by the engine |
| **R-17** | **All nine surfaces are built, and every screen is deeper; the prototype covers the whole advisor journey** | Nik asked to go deeper in each screen and build every surface discussed. BUILD-SPEC v2.1 was written first. New: `/pipeline` (prospects ranked by warmth of path, fit and size; drafted introduction asks, none for cold prospects), `/onboarding` (paperwork status by rule, escalated when unsigned more than 14 days; drafted reminders), `/servicing` (requests classified and routed with response targets; money movement requires a callback to a number on file), and a journey home page. Deeper: triage switches advisor and shows their day and last contact; the household page adds people with ages, history, notes, tasks, paperwork, requests and grounding documents; evidence adds history; proposals show the amount arithmetic; communications add talking points. New data (`prospects.json`, `service-requests.json`, `paperwork` per client) and engines each have tests. Everything still drafts; people send. The walkthrough gains a journey map and three chapters computed from the same data. PRD §4.1 updated: all nine are Build; roadmap order in §9.1 is unchanged |
